# 프리셋 진행도와 게임 제작 가능 범위

> 과거 기록입니다. 당시 제안·대기 상태·검증 결과를 보존하며 현재 사양은 [문서 안내](../INDEX.md)를 따릅니다.

기준: 2026-09-23. 아래 85%는 **스타터 프리셋 로드맵 1~6단계의 작업 범위**다. 새 게임 한 편의 개발 완료율을 뜻하지 않는다.

| 구분 | 지금 가능한 것 | 새 게임에서 해야 할 일 |
| --- | --- | --- |
| 시작·화면 | Boot 초기화, Title/Main 이동, 오류 차단, PC·가로형 모바일 예제 UI 안전 영역 | 게임 제목 화면의 디자인, 실제 HUD·메뉴·접근성 조정 |
| 설정 | 음량·전체화면·언어 코드 저장/복원과 시스템 적용 | 번역 데이터·글꼴·개별 오디오 채널·모바일 설정 UX |
| 진행 저장 | 단일 슬롯 JSON payload, 새 게임/이어하기, 버전·백업·손상 보호 | 캐릭터·스테이지·인벤토리 모델과 직렬화/복원, 저장 시점·다중 슬롯 정책 |
| 개발·검증 | Main 직접 Play의 격리 저장, 설정 검사, Windows 자동 테스트·개발 빌드 | 게임별 기능 테스트, 실제 화면·장치 테스트, 콘텐츠 제작 |

현재 상태에서 바로 시작하기 좋은 범위는 **오프라인 싱글 플레이 2D 게임의 프로토타입**이다. 퍼즐, 플랫폼 액션, 탑다운 액션, 턴제 RPG, 로그라이크·로그라이트처럼 서로 다른 장르도 같은 초기화·설정·저장 기반에서 출발할 수 있다. 다만 이동·전투·적 AI·스테이지 구성·랜덤 생성·성장·사망 규칙·퀘스트 등 플레이 자체는 아직 없다. 프리셋은 장르를 강제하지 않으므로 이 로직은 새 게임의 `Gameplay`에 구현한다.

3D 게임도 Core의 초기화·저장 계약을 재사용할 수 있지만 현재 URP 2D 렌더러·카메라·화면은 교체가 필요하다. 온라인 멀티플레이, 서버 동기화, 대규모 월드 저장, 모바일 스토어 배포·결제 등은 별도 아키텍처와 검증이 필요하다. Windows 빌드의 자동 저장·이어하기는 확인했지만 원본 Editor GUI, 실제 모바일 기기와 템플릿 배포는 아직 완료되지 않았다.

## 1920×1080 UI 기준의 의미

`1920×1080`은 Canvas Scaler의 **디자인 좌표 기준**이다. 실제 게임 화면을 최대 1920×1080으로 제한하지 않는다. 16:9 화면이 1280×720으로 줄면 UI의 상대적인 위치와 비율을 유지하며 픽셀 크기는 2/3가 된다. 960×540에서는 1/2이다. 비율이 다른 화면은 `StarterCanvasLayout`이 안전 영역 안에 콘텐츠를 맞추고 배경은 전체 화면을 채운다. 이 방식만으로 모든 해상도에서 동일한 가독성·터치 크기가 보장되지는 않는다. 새 HUD에는 앵커와 레이아웃 그룹, 긴 목록에는 스크롤/재배치를 설계하고 대상 해상도에서 확인한다.

## Walk·Attack·Hurt가 한 에셋에 들어 있는 경우

이 작업은 **프리셋이 완성된 뒤 새 게임 프로젝트에서** 제공받은 캐릭터 에셋으로 진행한다. 현재 스타터에는 특정 캐릭터의 Animator Controller나 동작 상태를 미리 넣지 않는다.

제공받은 파일의 구조를 확인하면 애니메이션으로 분리할 수 있다. 2D 스프라이트 시트라면 프레임을 자르고 Walk·Attack·Hurt를 각각 Animation Clip으로 만든 뒤 Animator Controller의 상태와 전환을 연결한다. Walk는 반복, Attack·Hurt는 보통 1회 재생으로 시작하고 이동·공격·피격 게임 로직과 연결한다. 공격 판정 프레임과 우선순위는 게임 규칙이 결정한다. 하나의 3D FBX 타임라인에 세 동작이 들어 있어도 프레임 범위를 나누어 클립으로 만들 수 있지만 현재 프로젝트의 2D 렌더링 구성은 별도 조정이 필요하다. 한 동작당 정지 그림 한 장뿐이라면 상태 전환은 가능해도 자연스러운 프레임 애니메이션에는 추가 프레임이나 리깅이 필요하다.

에셋을 받을 때 파일 형식(PNG 시트/개별 PNG/PSD/FBX 등), 각 동작의 프레임 순서·범위, 프레임 속도, 방향 수, 기준점·픽셀 단위, 반복 여부가 있으면 정확하게 설정할 수 있다. 정보가 없으면 실제 이미지를 분석해 초안을 만들고 게임 플레이에 맞는 전환·판정 시점을 확인한다. 에셋 제공 전에는 특정 프레임이나 애니메이션 결과를 확정할 수 없다.
