## 실제 구현 후속 — 2026-10-05

- 사용자 요청으로 선택한 좌측 메뉴형과 게임 시작/이어하기 분리를 반영했다. 저장은 **독립 진행 3개를 기본 정책**으로 구현했다.
- `StarterTitleMenu`는 New Game / Continue / Options / Credits / PC Quit와 목적별 슬롯 선택·관리·삭제 확인을 제공한다. 새 게임은 빈 슬롯, 이어하기는 저장 슬롯을 사용한다. 삭제는 Title의 별도 관리 화면에서 확인하며 기본 포커스는 Cancel이다.
- `GameSessionService`는 기본 3슬롯, 하나의 활성 `Current`와 nullable `CurrentSlotId`, 불변 슬롯 정보 목록을 제공한다. 기존 슬롯 1 파일과 스키마는 그대로 읽고 파일 2·3을 추가하며 settings.json은 공통으로 유지한다.
- 읽기·쓰기와 분리한 `IDeleteSaveFileStore`에서 정확한 백업·N형 GUID 보존/임시 파일을 먼저, 주 파일을 마지막에 삭제한다. 삭제 미지원 저장소는 다른 저장 기능을 유지하며 실패 결과를 알린다.
- 초기안에서 제안했던 `복구 → 이어하기 필수`와 달리 실제 저장 계약은 백업을 메모리로 읽어 이어가는 기존 동작을 유지한다. Recovered 슬롯은 명시적 복구 전에 저장할 수 없으며 Title 관리 화면에서 복구한다.
- **구현·필수 자동 검증 완료.** 아래 배치 대안·화면 전환·포커스 설명에는 초안 제안이 포함되므로 현재 동작의 확정 계약은 링크한 사용 가이드를 우선한다.

## 초기 조사와 화면 초안 기록

다음은 실제 구현 이전에 비교한 배치와 기능 제안이다. 이전의 브라우저 예시 데이터는 Unity 파일을 변경하지 않았다.

## 목표와 선택 사항

- PC와 **가로형 모바일**에서 사용할 수 있고, 이후 게임의 배경·로고·버튼 에셋을 교체하기 쉬운 메뉴를 만든다.
- 기존 `Screen Space Overlay`, `Scale With Screen Size`, **1920×1080 디자인 기준**, 안전 영역을 이어간다. 1920×1080은 최대 출력 해상도가 아니다.
- 저장 슬롯 3개, 슬롯별 저장 상태·이어하기·삭제를 제공하되 게임별 진행률·캐릭터·스테이지 규칙을 Core에 넣지 않는다.
- **선택된 배치는 좌측 메뉴형이다.** 메인 메뉴에서 `게임 시작`과 `이어하기`를 구분하며 각각 목적에 맞는 슬롯 선택 화면을 연다.
- **서로 독립된 진행을 담는 슬롯 3개를 기본 정책으로 구현했다.** 최초에는 권장 가정으로 제안했으며, 실제 구현 승인 이후의 범위를 이 기본값으로 진행했다. 하나의 진행을 여러 슬롯에 수동 복사하는 안과는 구분한다.

| 구분 | 독립 진행 슬롯 3개 — 현재 기본 정책 | 하나의 진행을 여러 시점에 수동 저장 — 대안 기록 |
| --- | --- | --- |
| 새 게임 | 빈 슬롯을 선택해 새 진행 시작 | 저장 대상 없이 시작할 수 있음 |
| 일반 저장 | 현재 진행에 연결된 슬롯에 기록 | 저장할 슬롯을 선택 |
| 세션 관계 | 슬롯마다 다른 진행·SessionId | 같은 SessionId가 여러 슬롯에 존재 가능 |
| 덮어쓰기 확인 | 다른 진행을 교체할 때 필요 | 같은 진행의 과거 시점도 확인 대상 |
| 기본 사용자 흐름 | 게임 시작 → 빈 슬롯 / 이어하기 → 저장 슬롯 | 저장 화면과 불러오기 화면의 목적을 구분 |

현재 코드의 `RequiresReplacement`는 SessionId가 다를 때만 확인을 요구한다. 수동 저장 방식을 선택한다면 같은 진행의 이전 시점도 덮어쓰기 대상으로 판단하도록 바꿔야 한다. 두 방식을 혼합해 자동으로 구현하지 않는다.

## 메인 메뉴 배치 비교 — 최초 검토 기록

아래는 최초 제안한 세 배치의 비교 기록이다. 이후 사용자가 A를 선택했고, 시작과 이어하기 입구도 분리하도록 요청했다. 현재 화면 기준은 다음 절을 따르며 B·C는 대안 검토 이력으로 남긴다. 장식 영역은 교체 가능한 배경·로고·일러스트를 위해 남긴다.

| 안 | 첫 화면 구성 | 이점 | 고려할 점 |
| --- | --- | --- | --- |
| **A. 좌측 메뉴형 — 최초 추천, 현재 선택** | 좌측 로고와 세로 `게임 시작 / 설정 / 제작진 / 종료`, 우측 배경·키 아트 | 가로 화면에서 메뉴 위치가 명확하고 게임 에셋을 교체할 공간을 확보하기 쉽다. | 좁은 화면에서는 장식 비중을 줄여 버튼과 문구의 크기를 유지해야 한다. |
| B. 중앙 메뉴형 | 중앙 로고 아래 세로 `게임 시작 / 설정 / 제작진 / 종료`, 배경은 전체 화면 | 현재 예제 구조에 가까워 변경 폭이 작고 시선이 한곳에 모인다. | 중앙 인물·장식이 있는 배경을 쓰면 메뉴와 시각적으로 겹칠 수 있다. |
| C. 슬롯 우선형 | 첫 화면에서 저장 슬롯 3개를 먼저 보여주고 설정을 보조 배치 | 플레이 버튼을 한 번 덜 눌러 진행을 선택할 수 있다. | 빈 슬롯·저장 정보·삭제 조작까지 첫 화면에 보여 정보량이 늘고 게임 로고·키 아트 공간이 줄어든다. |

`종료`는 PC에서 사용하는 메뉴다. 모바일에서는 플랫폼 흐름에 맞게 숨길 수 있도록 구성한다. 이 차이가 Core 저장 정책을 바꾸지는 않는다.

최초 A·B안은 하나의 플레이 입구 뒤 같은 슬롯 화면을 여는 구성이었다. 이번 수정으로 A는 아래의 `게임 시작 / 이어하기` 분리 방식으로 바뀌었다. 공통 슬롯 표시 컴포넌트를 사용하더라도 각 화면의 실행 목적과 허용 동작은 분리한다. 이 비교 단계에서는 화면 초안만 수정했고, 이후 실제 구현으로 진행한 상태는 문서 상단에 구분했다.

## 현재 선택된 메인 메뉴와 화면 목적

좌측 로고 아래 메뉴를 `게임 시작 / 이어하기 / 설정 / 제작진 / 종료` 순서로 세로 배치한다. 우측은 게임의 배경·키 아트를 연결하는 영역이다. `종료`는 PC에서 표시한다.

| 진입 | 표시하는 화면 | 선택 가능한 대상과 동작 |
| --- | --- | --- |
| 게임 시작 | 새 진행을 시작할 슬롯 선택 | 빈 슬롯만 새 게임 대상으로 선택한다. 저장이 있는 슬롯은 비활성화하고 기존 진행이 있다는 설명을 보여준다. |
| 이어하기 | 저장된 진행을 복원할 슬롯 선택 | 정상 저장 슬롯을 선택해 복원한다. 빈 슬롯은 비활성화하고 저장 데이터가 없다고 표시한다. |
| 슬롯 관리 | Title 안의 별도 관리 화면 | 저장 상태 확인과 명시적 삭제를 제공한다. 시작·이어하기 화면의 보조 `슬롯 관리`로 진입하며, 선택 즉시 게임을 시작하지 않는다. |
| 설정 | 공통 설정 화면 | 설정 변경 후 이전 메뉴로 돌아간다. |
| 제작진 | 제작진 표시 화면 | 확인 후 이전 메뉴로 돌아간다. |

게임 시작·이어하기·슬롯 관리는 모두 슬롯 1·2·3을 같은 순서로 표시한다. 현재 목적에 맞지 않는 슬롯을 숨기지 않고 상태를 설명하되, 실행 버튼은 비활성화한다. 키보드·게임패드의 실행 포커스는 비활성 버튼을 건너뛴다.

- **모두 비어 있음:** 메인 메뉴의 `이어하기`를 비활성화하고 저장된 진행이 없다는 설명을 표시한다. 첫 실행의 기본 포커스는 `게임 시작`이다.
- **모두 사용 중:** `게임 시작` 화면은 세 슬롯의 상태와 `빈 슬롯이 없습니다` 안내를 보여주고 `슬롯 관리`로 이동할 수 있게 한다. 이때 시작 화면의 초기 실행 포커스는 `슬롯 관리`다. 새 게임을 누르는 것만으로 기존 진행을 덮어쓰지 않는다.
- **백업만 복구 가능:** `이어하기` 경로는 열어 해당 슬롯에 `복구 필요`를 표시하되 즉시 복원하지 않고 명시적 복구를 먼저 안내한다.
- **정상 저장·복구 가능한 백업이 모두 없음:** `이어하기`는 비활성화한다. 손상·호환 불가·접근 오류는 저장이 없다는 상태와 구별하고 `게임 시작 → 슬롯 관리`에서 확인할 수 있게 한다.

관리 화면은 어디서 들어왔는지 기록한다. `뒤로`는 시작 화면 또는 이어하기 화면으로 돌아가 상태를 다시 계산한다. 슬롯의 상태가 바뀌었을 때 사용할 수 없어진 버튼으로 포커스를 되돌리지 않는다.

## 공통 슬롯 선택 화면

- 넓은 가로 화면: 같은 크기의 **슬롯 카드 3개를 가로 배치**한다.
- 가용 안전 영역이 좁은 가로 화면: **슬롯 3개를 세로 목록 형태로 재배치**하는 안을 검토한다. 세로 방향 지원을 의미하지 않는다.
- 전환 기준은 기기 이름이 아니라 안전 영역 안에서 카드·문구·조작 영역을 충분히 표시할 수 있는지로 정한다. 구체 임계값은 실제 에셋·글꼴을 연결할 때 확정한다.
- 전체 화면 배경과 조작 콘텐츠를 분리한다. 화면 비율이 달라져도 배경은 화면을 채우고 카드·버튼은 안전 영역 안에 둔다.
- 기본 정보는 `슬롯 1/2/3`, 저장 상태, 마지막 저장 시각이다. 저장 시각은 현재 `SavedUtc`를 표시 형식으로 변환하며 저장 파일의 UTC 값은 유지한다.
- 초상화·진행률·플레이 시간·스테이지명은 게임별 제공 정보다. 값이 없을 때 임의의 샘플 수치나 빈 필수 필드를 표시하지 않는다.

| 슬롯 상태 | 카드 표시 | 게임 시작 화면 | 이어하기 화면 | 별도 슬롯 관리 화면 |
| --- | --- | --- | --- | --- |
| 비어 있음 | 슬롯 번호, 비어 있음 | 새 게임 가능 | 비활성·저장 데이터 없음 | 삭제 비활성 |
| 정상 저장 | 슬롯 번호, 마지막 저장 시각 | 비활성·사용 중 | 선택 후 복원 가능 | 삭제 확인 |
| 백업 복구 가능 | 복구할 백업이 있다는 설명 | 비활성·복구 데이터 있음 | 명시적 복구 후 이어하기 | 삭제 확인 |
| 손상·호환 불가 | 읽을 수 없는 이유의 짧은 설명 | 비활성·관리 필요 | 복원 비활성·관리 안내 | 확인 후 삭제; 자동 덮어쓰기 금지 |
| 접근 오류 | 파일에 접근할 수 없다는 설명 | 시작 비활성 | 복원 비활성·재시도 | 재시도; 성공을 확인할 수 없는 삭제는 완료로 표시하지 않음 |

다른 슬롯 하나가 손상되거나 호환되지 않더라도 빈 슬롯의 새 게임과 정상 저장 슬롯의 이어하기는 사용할 수 있어야 한다. 삭제는 시작·이어하기 선택과 분리된 관리 화면에서 실행하고 항상 확인창을 거친다.

## 독립 슬롯 방식으로 제안한 사용자 흐름

1. 새 진행은 `메인 메뉴 → 게임 시작 → 빈 슬롯 선택 → 새 진행 시작`으로 진입한다.
2. 저장된 진행은 `메인 메뉴 → 이어하기 → 저장 슬롯 선택 → 해당 진행 복원`으로 진입한다.
3. 게임의 `저장`은 활성 슬롯에만 현재 payload를 기록한다. 다른 슬롯을 자동으로 덮어쓰지 않는다.
4. 저장 정리는 `게임 시작 또는 이어하기의 슬롯 화면 → 슬롯 관리 → 삭제 확인 → 취소 또는 삭제`로 구분한다.
5. 메인 메뉴로 돌아가면 저장 목록을 다시 확인해 `이어하기` 활성 여부를 갱신한다. 다른 슬롯으로 시작하거나 이어갈 수 있다.

새 게임을 시작하는 것만으로 파일을 쓰지 않는 현행 원칙을 유지하는 초안이다. 따라서 첫 명시적 저장 전에 종료하면 해당 슬롯은 다시 비어 있다. 자동 저장 시점은 게임에서 정하며, 이 초안에서는 추가하지 않는다. 기본 저장 버튼 역시 게임 오브젝트를 자동 수집하지 않고 게임 코드가 전달한 payload를 저장한다.

현재 구현은 백업을 메모리로 읽어 이어하기도 허용하지만 저장 전에는 명시적 복구를 요구한다. 새 슬롯 UI는 상태 혼동을 줄이기 위해 `복구 → 이어하기`를 안내하는 흐름을 우선 제안하며, 이는 초기 UI 제안이며 실제 구현은 상단에 정리한 백업 메모리 이어하기 계약을 유지한다.

## 삭제 확인과 실패 처리

삭제 위치는 **Title 안의 별도 슬롯 관리 화면**으로 제한한다. 게임 시작·이어하기 슬롯을 누르는 동작으로 삭제가 실행되지 않으며, 실행 중인 진행의 슬롯을 게임 안에서 삭제하는 동작은 넣지 않는다.

확인창은 대상 슬롯 번호와 마지막 저장 시각을 다시 보여주고, 해당 슬롯의 진행과 복구용 백업도 제거된다고 설명한다. 버튼은 `취소 / 삭제`로 구분하며 **초기 포커스는 취소**다. Esc·뒤로·게임패드 취소는 모두 창을 닫고 슬롯 관리의 원래 선택 슬롯 카드로 포커스를 돌려준다. 확인창이 떠 있는 동안 뒤쪽 슬롯을 선택하거나 다른 버튼을 실행할 수 없어야 한다.

현행 Repository는 주 파일이 없으면 `.bak`을 조회한다. 따라서 주 파일만 삭제하면 이전 진행이 복구 가능 상태로 다시 나타날 수 있다. 구현 시 다음 계약이 필요하다.

- 확인창을 열 때 슬롯 ID를 고정하고 실행 직전 유효 범위·상태를 다시 확인한다.
- 선택 슬롯의 `.bak`, `.preserved-*`, `.tmp`를 정확한 파일명 범위로 처리하고 주 파일은 마지막으로 삭제한다. 다른 슬롯과 `settings.json`은 대상에 포함하지 않는다.
- 보조 파일 정리가 실패하면 주 파일 삭제를 진행하지 않고 오류를 표시한다. 이미 정리된 일부 보조 파일까지 모두 원상복구되는 트랜잭션으로 설명하지 않는다.
- 삭제 성공 뒤 슬롯 목록·선택된 진행의 캐시를 갱신한다. 재실행 시 백업을 통해 진행이 재등장하지 않는지 확인한다.
- 강제 종료 시점까지 여러 파일 삭제를 하나의 작업처럼 확정해야 한다면 별도 삭제 기록이 필요하다. 이번 최소 초안은 모든 정전·강제 종료 상황의 원자적 삭제를 보장하지 않는다.

### 상태 변경 이후의 포커스

- 삭제 취소: 관리 화면의 원래 선택 슬롯 카드로 돌아간다. 해당 카드를 사용할 수 없으면 다음 사용 가능한 슬롯, 없으면 `뒤로`를 선택한다.
- 삭제 성공: 관리 화면에서는 방금 비워진 카드도 선택할 수 있으므로 같은 카드에 포커스를 유지하고 삭제 결과를 표시한다. 비활성화된 삭제 실행 버튼에 포커스를 두지 않는다.
- 관리에서 게임 시작 화면으로 복귀: 방금 비운 슬롯을 우선 선택하고, 그 슬롯을 사용할 수 없으면 다음 빈 슬롯, 모두 사용 중이면 `슬롯 관리`를 선택한다.
- 관리에서 이어하기 화면으로 복귀: 다음 복원 가능 슬롯을 선택한다. 모두 비었거나 복원할 수 없으면 상태 안내와 세 슬롯을 유지하고 `뒤로`에 포커스를 둔다.
- 메인 메뉴로 복귀: 호출했던 `게임 시작` 또는 `이어하기`로 돌아간다. 마지막 저장 삭제로 `이어하기`가 비활성화되었다면 `게임 시작`에 포커스를 둔다.

## 기존 저장 호환성과 코드 확장 방향

기존 `save-slot-1.json`을 슬롯 1로 유지하고 `save-slot-2.json`, `save-slot-3.json`을 추가한다. 기존 JSON schemaVersion 2·payloadVersion·슬롯 1 백업을 유지하므로 슬롯 추가만을 위해 파일을 이주하거나 게임 payload에 슬롯 번호를 강제로 넣을 필요가 없다. `settings.json`은 슬롯 공통 설정이다.

| 책임 | 제안 |
| --- | --- |
| `GameSessionService` | 하나의 활성 `Current`와 `CurrentSlotId`, 읽기 전용 슬롯 정보 목록을 제공한다. 슬롯별 읽기 결과를 분리하고 성공 후에만 활성 상태를 바꾼다. |
| 슬롯 API | `StartNew(slotId)`, `TryContinue(slotId)`, 활성 슬롯 `TrySave(...)`, `TryRecoverBackup(slotId)`, `TryDelete(slotId)` 형태를 검토한다. 이름·오버로드는 구현 시 기존 호출 호환성을 함께 점검한다. |
| 저장소 경계 | `JsonRepository<T>`의 파일명별 저장·복구를 재사용한다. UI가 파일 경로를 전달하지 않고 서비스가 검증한 슬롯 번호로 파일명을 만든다. |
| 삭제 capability | 읽기·쓰기용 `ITextFileStore`와 구분되는 작은 삭제 capability를 주입한다. 기존 대체 저장소가 삭제를 지원하지 않으면 그 기능을 명시적으로 비활성화한다. |
| `AppRoot` | 서비스 조립·수명과 Title/게임/전환 상태의 실행 허용 여부를 조정한다. 삭제 확인창의 위치·스타일을 소유하지 않는다. |
| 예제 UI | 상태 표시·선택·확인·취소를 담당한다. 별도 게임 UI로 바꿔도 슬롯 API를 그대로 사용할 수 있게 한다. |

수량 3은 예제 구성값으로 두되, 플레이 시간 수집이나 캐릭터 모델처럼 게임별 기능을 서비스에 함께 추가하지 않는다. 기존 단일 슬롯 호출의 호환 래퍼가 필요하다면 명시적인 슬롯 1 기본 동작으로 유지하고, 어느 슬롯인지 모호한 자동 선택은 피한다.

### SOLID와 적용할 패턴

- **단일 책임:** 세션·슬롯 정책, 파일 작업, 앱 흐름, 화면 표현을 나눈다.
- **개방·폐쇄:** 게임별 저장 정보와 화면 에셋을 확장할 수 있고, 저장소를 교체해도 UI의 파일 접근 코드를 고칠 필요가 없도록 한다.
- **리스코프 치환:** 대체 저장소는 누락·접근 실패·검증 실패·삭제 범위·실패 결과 계약을 지켜야 한다. 기존 파일 보존이나 삭제 성공을 구현과 다르게 보고하지 않는다.
- **인터페이스 분리:** 슬롯 삭제가 필요해졌다는 이유로 모든 설정 저장 소비자에게 삭제 기능을 강제하지 않는다.
- **의존성 역전:** 앱 서비스가 파일 시스템을 직접 조작하지 않고 주입된 저장·삭제 경계에 의존한다.

현재의 Composition Root/Application Controller, Observer, payload 검증 Strategy, 파일 저장 Adapter와 제한된 Repository 형태를 확장하면 충분하다. 슬롯 3개를 위해 DI 컨테이너·전역 이벤트 버스·별도 상태 클래스 체계를 새로 넣을 필요는 없다.

## 초안에서 정한 필수 검증 범위

1. 기존 슬롯 1의 정상·백업 저장을 읽고 슬롯 2·3의 저장·로드가 서로 격리되는지 확인한다. 기존 설정 파일은 유지한다.
2. 게임 시작은 빈 슬롯만, 이어하기는 저장된 진행만 선택할 수 있는지 확인한다. 세 슬롯의 새 게임·저장·재실행·이어하기에서 올바른 활성 슬롯과 payload가 복원되는지 확인한다.
3. 삭제 취소·확정, 잠긴 백업/주 파일의 삭제 실패, 삭제 후 재실행 시 미복구, 다른 슬롯·설정 보존을 확인한다.
4. 손상·버전 불일치 슬롯의 자동 덮어쓰기를 막으면서 다른 정상 슬롯은 사용할 수 있는지 확인한다.
5. 모두 빈 상태의 이어하기 비활성, 모두 사용 중일 때 시작 화면의 관리 연결, 마지막 저장 삭제 후 포커스 복귀를 확인한다. 씬 전환·확인창의 중복 입력을 막고 키보드·게임패드·포인터가 같은 선택/취소 흐름을 따르는지 확인한다.
6. 1920×1080과 좁은 가로 화면·안전 영역에서 3개 슬롯과 확인창의 문구·버튼이 잘리지 않는지 확인한다. 최종 에셋의 실제 터치 가독성은 대상 기기에서 확인한다.

이전의 통합 진입 대화용 초안에서는 3개 슬롯 표시, 선택 슬롯 저장, 삭제 취소·대상 격리, 취소 기본 포커스와 좁은 표시 폭의 버튼 영역, 스크립트 오류 부재를 브라우저에서 확인했다. 이 기록은 이번 시작/이어하기 분리와 별도 슬롯 관리 흐름의 검증을 대신하지 않으며 Unity 저장 코드나 실기기 검증 결과도 아니다.

2026-10-05 수정 초안에서도 시작은 빈 슬롯만 선택, 이어하기는 저장 슬롯만 선택, 선택한 진행 복원·저장, 모두 사용 중/빈 상태, 슬롯 관리와 삭제 취소·포커스 복귀·대상 격리, 좁은 표시 폭과 스크립트 오류 부재를 브라우저에서 확인했다. 실제 Unity 저장·삭제 검증은 아직 수행하지 않았다.

위 목록은 초안에서 정한 실제 구현의 검증 범위다. 현재 실제 구현은 완료했으며 검증 결과는 별도로 기록할 예정이다. 브라우저 초안에서 통과한 항목을 완성된 Unity 기능의 테스트 수치로 집계하지 않는다. 대화용 화면 예시를 제공한다면 별도 HTML 아티팩트의 임시 예시 데이터만 사용하며 실제 게임 저장이나 Unity 메뉴를 조작하지 않는다.
