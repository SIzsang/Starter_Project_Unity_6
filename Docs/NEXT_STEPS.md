## 1. 현재 소스·문서 기준 정리 — 완료

실행·진단 기반 / Editor 개발 도구 / 선택형 Pool / 문서·인계의 네 커밋으로 분리했다. 신규 코드·메타를 추적하고 README·Summary·새 게임 가이드의 현재 시작점을 정리했다. 현재 C#/asmdef 60개는 Gate 검증 소스와 일치하며 스크립트 메타 누락·중복 GUID는 없었다. 사용자 ProjectSettings Cloud 변경은 보존하고 커밋에서 제외했다. 아래는 완료 범위와 운영 기준이다.

Phase 2~4의 실제 변경을 코드·씬/에셋·메타·문서·사용자 설정으로 분류한다. 신규 파일이 커밋 대상에서 빠지지 않는지, 파일과 폴더의 메타가 맞는지, Core/UI/Editor/Pooling의 어셈블리 경계가 문서와 같은지 확인한다.

README와 새 게임 진입 문서에서 현재 구현의 출발점을 찾기 쉽게 정리한다. 3슬롯 저장, SceneRoot, Definition/Runtime, 입력 컨텍스트, Pause/Audio, 개발 도구, 선택형 Pool 안내를 연결한다. 과거 v1.0.0의 단일 슬롯 설명·당시 검증·배포 기록은 해당 버전의 이력으로 남기고 현재 사양과 구분한다.

산출물은 변경 파일 분류와 Git 반영 대상 목록, 현재 기능으로 이어지는 문서 진입점이다. 개인 Cloud ID와 사용자 변경은 별도로 식별한다. 소스 커밋은 이 목록을 기준으로 수행하며, 커밋 제목은 영어·설명 본문은 한국어로 작성한다. 이번 문서 최신화는 원격 main 동기화를 포함한다. 새 태그·Release는 별도 버전 배포 요청 시 진행한다.

완료 기준: 이후 Work가 어떤 소스와 문서를 기준으로 시작해야 하는지 명확하고, 신규 구현·메타의 인계 누락과 과거 버전 혼동이 없는 상태. 문서 정리에는 Unity 실행 검증을 추가하지 않는다. 의존성·설정의 실제 문제를 발견한 경우에만 해당 위험을 따로 확인한다.

## 2. 작은 Game Layer 적용 사례

실제 제작할 게임이 정해지면 그 게임의 가장 작은 플레이 흐름을 먼저 연결한다. 아직 게임이 정해지지 않았다면 기본 조작 하나·변경되는 상태 하나·반복 생성되는 효과 하나 정도의 작은 사용 예제로 범위를 제한한다. 콘텐츠와 장르 규칙은 Game Layer에 둔다.

- SceneRoot 하나에서 초기화·진입·종료를 연결하고, 앱의 공개 요청 API로 시작·Title 복귀를 처리한다.
- Definition은 읽기 전용으로 사용하고 플레이 중 값은 Runtime에 둔다. 게임별 payload의 초기값·저장 필드·버전·검증 규칙을 연결한다.
- Gameplay 입력과 Pause, BGM/SFX/UI Audio를 게임의 실제 조작에서 사용한다.
- 반복 효과가 필요한 경우 Pool을 연결한다. Game Layer가 reset·스폰·반납 시점·재고 상한을 결정한다.
- 씬 종료 시 비동기 작업·입력 범위·대여 객체를 정리한다. Pool 반납 뒤 돌아오는 비동기 결과는 씬 토큰과 lease 유효성을 확인한다.

완료 기준: Boot → New Game → 조작/상태 변경 → 명시적 저장 → Title → Continue에서 같은 상태가 복원되고, 씬을 나간 뒤 작업이나 대여 객체가 남지 않는다. 샘플의 게임 규칙 없이도 Starter Core를 사용할 수 있어야 한다.

이 작업은 기존 API를 모두 다시 테스트하는 단계가 아니다. 적용 과정에서 드러난 연결 문제를 검토하고, 저장·씬 수명처럼 코드만으로 판단하기 어려운 부분만 해당 실행 경로로 확인한다. Pool 성능·Prewarm 수량은 실제 콘텐츠와 대상 기기가 정해진 뒤 측정으로 결정한다.

## 3. 필요한 Player·개발 도구 확인

실제 인계 또는 첫 게임 적용 시점에 한 번의 확인 단위를 잡는다. 기존 Windows 환경을 기본 후보로 삼되, 새 대상 플랫폼이 정해지면 그 요구로 범위를 바꾼다.

먼저 실제로 사용할 Development Player에서 앱 시작·새 게임·저장·프로세스 재시작·Continue를 확인한다. 현재 빌드 구성의 환경 심볼·기본 로그 수준·출력 경로가 Player에 반영되는지도 확인한다. Release 전달 시에는 Release 구성과 Editor 전용 코드의 제외를 확인하고, QA 구성을 사용할 경우에만 QA의 해당 옵션을 확인한다. 세 빌드 환경과 전체 테스트를 기능 변경마다 반복하지 않는다.

수동 확인은 실제 사용 경로에 한정한다. 키보드/마우스와 필요한 게임패드로 Gameplay·Pause·UI의 입력 전환을 확인하고, Pause/복귀의 시간 및 BGM/SFX 동작과 UI Audio를 직접 확인한다. 합성 입력·Unity 이벤트 결과와 실제 장치 결과를 구분해 기록한다.

Editor 도구는 Main 직접 Play/종료 후 시작 씬 복원, 개발 저장소 격리, Reset Test Data의 취소·백업, Debug 입력 범위 해제처럼 실제 사용할 핵심 경로를 확인한다. 이미 자동 검증된 경로는 사용상 불확실성이 있을 때만 추가 확인한다.

완료 기준: 선택한 사용·인계 환경의 실제 결과와 제한이 최신 검증 문서에 남아 있다. 실제 사용자 데이터에 쓰지 않는 독립 저장소로 확인한다. 모바일 빌드·터치·Safe Area 실기기 확인은 모바일 게임을 선정한 시점의 작업이다.

## 4. 새 소스 버전·인계 정리

소스 정리와 적용 과정의 필요한 보완이 끝나면 현재 구현을 재현할 수 있는 커밋을 기준으로 인계한다. 새 버전 번호는 실제 변경 범위와 배포 시점에 결정하고, 기존 v1.0.0 태그·ZIP은 해당 버전으로 유지한다.

새 게임에서 바꿀 Company/Product/Application Identifier와 Cloud 연결, 초기 씬·데이터·payload 연결 지점을 안내한다. Pool은 선택 모듈로 사용 여부와 어셈블리 참조 방법을 명시한다. 사용 예제의 게임 규칙과 개인 프로젝트 식별자가 범용 인계물에 섞이지 않게 한다.

완료 기준: 버전/소스 커밋, 포함 기능, 새 프로젝트 시작 방법, 실제 검증 범위가 일치한다. 패키지 복원·메타 누락 등 새 복제로만 확인 가능한 위험이 있을 때만 깨끗한 복제본 확인을 수행한다. 만든 임시 복제본은 결과 기록 후 정리하고, 분석상 유지가 필요하면 위치·목적·삭제 조건을 체크포인트에 남긴다.

GitHub Template 기능 설정과 기존 Release를 다시 만드는 것은 남은 필수 작업이 아니다. 현재 main 동기화와 버전 Release는 구분한다. 새 태그·Release ZIP은 별도 배포 범위를 확정한 뒤 생성한다.

## 보류 후보를 다시 선정하는 조건

| 후보 | 작업을 시작할 실제 조건 |
| --- | --- |
| Localization | 실제 다국어 콘텐츠와 공통 문자열/테이블 관리가 필요할 때 |

| Input Rebinding / Device Detection | 사용자 키 저장이나 장치 변경에 따른 버튼 안내가 필요할 때 |
| Asset Provider / Addressables | 콘텐츠 규모·비동기 로딩·메모리 해제·원격 배포 요구가 확인될 때 |

현재 위 후보를 필수 구현으로 올릴 근거는 없다. Combat·Inventory·Quest·AI·캐릭터 성장과 같은 게임 규칙은 해당 게임에서 구현한다. 여러 게임에서 반복 필요가 확인되면 그때 별도 Gameplay Module로 검토한다.
